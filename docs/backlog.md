# Backlog（想过、判断为"现在不做"的东西）

> PLAN 第 2 节的规定：D16–D18 只修 bug，不加功能。任何"顺手加一个"的念头写在这里，不当场做。
> 每条必须写清：**想做什么、为什么现在不做、什么条件下值得做。** 只写"待办"两个字的条目不成立——
> 那等于把决定推给未来的自己，而未来的自己不在场。

## 1. 真正裁剪超过 1 MB 的结果（D13 遗留）

- **想做什么**：`MAX_RESULT_BYTES` 现在是**标记**不是**裁剪**。超限的 payload 依然整份交给模型。
- **为什么现在不做**：裁剪必须在计算 `result_digest` **之前**发生，否则记录里的摘要与模型实际看到的字节不再对应——那会动到 D4 立下的 fail-closed 顺序（"先落盘、后交付"）。这不是一行代码，是一次顺序变更，D13 的判据（`truncated` 不污染证据）也不要求它。
- **什么条件下值得做**：接入真实上游、且实测出现过单次结果撑爆上下文的时候。届时判据是："被裁剪的结果，`result_digest` 等于模型实际收到的字节的摘要"——一条可以写成断言的句子。

## 2. 按形状打分选正文块（D13 遗留）

- **想做什么**：`_body_of` 取"第一个可解析的块"。改成在有多个可解析块时，选最像正文的那个（键集合命中已声明 shape 的数量）。
- **为什么现在不做**：这是准入/选择逻辑（同一类问题由 D14 的 BM25 选择器负责），塞进证据层会让"抽取器是纯函数"这条性质变成"抽取器需要知道已声明 shape 的分布"。而且当前没有观察到真实上游有 JSON 横幅。
- **什么条件下值得做**：出现一个"正文前面带 JSON 元数据"的真实上游，且 `evidence_added` 为空但调用明显有答案。届时先补一条与 `test_a_json_preamble_wins_and_that_is_a_known_limit` 相反的用例，再改实现。

## 3. 上游幂等性声明 + 可重试超时（D13 遗留）

- **想做什么**：DESIGN 2.6 原来写的是"超时重试"。现在记成一次失败，因为超时不告诉你调用有没有执行。
- **为什么现在不做**：需要协议侧的幂等性标注（`Tool.annotations` 里没有这层语义），否则网关无法判断重试是否安全；对非只读工具，重试是语义错误。
- **什么条件下值得做**：上游在 `tools/list` 里显式声明 `idempotent: true`（或等价扩展），且网关能把"重试过"写进 `decision`——否则"回填"与"重算"在事后无法区分（同局限 8）。

## 4. 跨 run 的合并视图（D15 遗留）

- **想做什么**：现在一条轨迹一个页面；同一话题换了两次问法就有三个 run 文件，只能开三个标签页对照。想按 `parent_run_id` 把一条会话的多个 run 串成一个页面，左栏按会话分组。
- **为什么现在不做**：D10 定的是"一个 run 一个文件"，`task_id` 与 `parent_run_id` 在记录里已经足够反查（`session_id` 也能分组），缺的只是视图。而视图做错的代价比缺一个视图高：把不同 run 的步"接起来"会诱导人读成一条连续的推理，而它们之间恰恰没有偏序。
- **什么条件下值得做**：出现真实的追问链（同一会话 ≥ 3 个 run）需要在一次讲解里展示"继承了什么、重读了什么"。届时判据是：合并页面必须能与单独打开每个 run 得到**逐字段相同**的结论——否则合并就引入了新的解释。

## 5. 回放视图的"复制这一条为断言"（D15 遗留）

- **想做什么**：点一条记录，把它的 `offered` / `chosen` / `stop_check` 生成一段可以直接粘进测试的断言代码。
- **为什么现在不做**：这是把"看"变成"写"，而写测试该发生在读代码的时候、有上下文；从页面里复制一段断言，最容易的结果是复制出**当前行为**而不是**期望行为**——那正是本项目一直在防的"把现状当真理"。
- **什么条件下值得做**：等 `tests/fixtures/` 那套（D12）需要更多"真实轨迹断言"样本时，做成 `scripts/make_fixtures.py` 的一个开关，而不是页面上的按钮。

## 6. 规则超时，以及"失灵时往哪边倒"（D17 遗留）

- **想做什么**：给每条规则一个超时；超时后不是崩溃，而是按规则自己声明的方向倒：安全检查（R1/R5）**停机**，完整性/进度规则（R2/R3/R4）**放行并标 `rule_timeout`**。DESIGN 1.5 那张表写的"保守放行"只对后一类成立。
- **为什么现在不做**：两个原因。一是超时机制本身是新结构——每轮计时、超时后 `attempted` 怎么记、`stop_check` 里多一个键（= schema 版本升级），都在缓冲期的"只修 bug"之外。二是**当前没有一条规则会慢**：它们是纯函数，跑在冻结的 `StopContext` 上，实测单次判定在微秒级。给不存在的病开药，只会多一条没人验证的分支。
- **什么条件下值得做**：接上一条真会慢的规则（要读网络、要算大集合）时；或者崩溃策略要细化时——D17 统一按"停机"处理，原因是"崩溃"与"超时"不是一回事（前者意味着这条规则永远不会给答案），代价是 R4 崩了也停。届时判据：**一条故意 sleep 的假规则必须被超时拦住，且轨迹里能看出是超时、不是崩溃、不是命中。**

## 7. 写入器的文件锁（D17 遗留）

- **想做什么**：`JsonlSink` 现在靠"文件大小变了"**发现**并发写者，不阻止。改成真正的互斥（Windows 用 `msvcrt.locking`，POSIX 用 `flock`，或一个 `.lock` 旁路文件）。
- **为什么现在不做**：一个 run 一个文件，写入者是单进程；现有的发现机制已经保证"后动手的那个会喊"，而链不会因此变脏。锁会引入新的失败模式（陈旧锁、NFS、进程崩溃后锁泄漏），每一个都要单独的判据——这比它防的问题更大。
- **什么条件下值得做**：出现"多个进程写同一个 `trace_dir`"的真实用法（例如一队 agent 共享目录）。届时判据是：**两个进程各写 100 条，最终文件里 200 条、`verify` 通过、无重复 `seq`**——现在这条只能做到"其中一个报错退出"。

## 8. 把停机通知也放进 `_meta`（D18 遗留）

- **想做什么**：通知现在只有一条信道——结果里追加的 `TextContent`。agent 读它，模型也读它。想让 agent 读一份上游写不到的副本：在 `CallToolResult._meta` 里同时放 `gateway.notice`，agent 优先读那份。
- **为什么现在不做**：`_meta` 会进 `result_payload()`（`model_dump()` 的结果），也就是进 `result_digest`——加字段等于改被哈希的形状，要么升 schema 版本，要么在算摘要前把 `_meta` 摘掉（后者是"摘要只覆盖上游说的那部分"的一次重新定义）。两者都超出缓冲期"只修 bug"的范围，而且当前没有伪造案例，只有一条推理。
- **什么条件下值得做**：接上一个**会返回用户可控文本**的上游（issue 正文、日志、网页正文）时。届时判据：**把伪造通知塞进工具结果的正文，agent 的 `stop_reason` 不变、`halt` 为空；而真停机时两份信道给出逐字段相同的通知。** 顺带把"通知可有可无"这条也钉住：`_meta` 缺失时退回文本块，不能因此静默不报停机。

## 9. `ref-depth-exceeded` 这个名字（D18 遗留）

- **想做什么**：`_resolve_refs` 的 `depth` 是**所有**递归的深度，不只是 `$ref` 链的深度。于是一个 33 层嵌套 `items` 的合法 schema 会被就地截成 `{}`，note 写的是 `ref-depth-exceeded`——一句不描述实际发生的事的话。改名（或拆成两个上限：ref 链深度与结构深度）。
- **为什么现在不做**：33 层嵌套在真实 server 里没见过（探针是从 100 层起试的），而拆分上限会改变既有 schema 的归一化结果 = 改变 `schema_hash` = 让 `config/schema-manifest.json` 全线漂移一次。为了一个没人遇到的名字做一次全局 re-freeze，代价与收益不成比例。
- **什么条件下值得做**：遇到真实上游的深层 schema 被截断（表现为"工具的参数突然没了"）。届时先确认是深度问题还是 `$ref` 环问题，再决定是改名还是拆上限；无论哪种，都要同时更新 manifest 并把旧轨迹的可比性说清。

## 10. `/play` 一次跑一条，没有队列也没有并发上限（D19 遗留）

- **想做什么**：`/play` 现在每点一次就 `asyncio.run` 一个 run，跑的时候请求线程被占满 5–10 秒。连点两次会同时跑两个 run（各写各的文件，互不干扰，但抢 CPU），没有队列、没有并发上限、没有进度上报。
- **为什么现在不做**：本地单人工具，一次一条任务是它唯一诚实的使用方式。加队列要引入"排队中/运行中/失败"三个新状态和一个轮询端点，而这三种状态没有一个能改进"看着它跑"这件事——真需要的话，用户会同时开两个终端。
- **什么条件下值得做**：出现"一次要看完整批 20 条"的需求（那时正确的形态不是队列，而是 `scripts/experiment.py` 的结果页，一次跑批、一次看表）。届时判据：**20 条任务串行跑完的总时间有上界，中途失败的那条不影响其余，页面上每条都有独立的 verdict。**

## 11. `/play` 的帧只覆盖"调用"，不覆盖"网关内部决定"（D19 遗留）

- **想做什么**：现在每帧是一行调用（工具、参数、结果、窗口大小、证据增量）。网关在两次调用之间还做了别的事：建索引、算 q、`sticky_seed` 合并窗口、pin 占槽位。这些都在 `selector.py` 里可离线复算，但页面上看不见。
- **为什么现在不做**：一旦把"为什么这 5 个工具被选中"画出来，页面就要解释 BM25 的打分，而打分是 20 行 Python 加一个语料——**解释成本高于被解释的东西**。当前页面的论点是"窗口收窄了"，不是"收窄得对不对"；后者由 `gating_demo.py` 的离线复现负责（65/65 逐字一致）。
- **什么条件下值得做**：有人质疑"这 5 个是不是碰巧"的时候。届时正确做法不是画词云，而是**点某一步跳到 `gating_demo` 的离线重排输出**，让两边逐字对照。
