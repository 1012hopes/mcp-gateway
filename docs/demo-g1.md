# G1 演示脚本（照着念）

> 目标：在 30 秒内让人相信「这条轨迹证明得了发生过什么，也证明得了没发生过什么」。
> 全部命令都在 `E:\mcp-gateway` 下执行，需要一个装了 `mcp` 的解释器（`.venv`）。

## 0. 准备

```powershell
# 一条命令跑完整套：正常运行 / 真实拔权限 / 注入写盘失败
.venv\Scripts\python.exe scripts\failclosed_demo.py

# 真实跑一轮，产出带 offered 的轨迹
.venv\Scripts\python.exe scripts\echo_client.py
```

`echo_client.py` 会把 run id 打在最后一行，形如 `run-1797b64ba398`。下面用 `<RUN>` 代替。

## 1. 先证明链是好的

```powershell
.venv\Scripts\python.exe -m gateway.trace verify traces\runs\<RUN>.jsonl
```

```
[PASS] traces\runs\<RUN>.jsonl
  OK: 5 条记录，链完整
  note: 链完整只证明「已记录的部分没被改过」……
```

**台词**：链完整这句话是有范围的，`note` 自己就把范围说出来了。我不希望别人看到一个 PASS 就以为“什么都没少”。

## 2. 攻击一：改字段（最朴素的篡改）

```powershell
.venv\Scripts\python.exe scripts\tamper_demo.py --path traces\runs\<RUN>.jsonl
```

```
[2] 中间行字段：把 seq 3 的 chosen 换掉
    -> 检出  seq=3  hash_mismatch
```

**台词**：改了内容但没动哈希，第 3 行自己就对不上自己，报的就是第 3 行。

## 3. 攻击二：改字段并重算哈希（关键的那一步）

```
[7] 改字段并重算：改 seq 3 的 chosen 并重算它的 hash -> 断在下一行
    -> 检出  seq=4  prev_hash_mismatch
       prev_hash 未指向 seq=3 的哈希
```

**台词**：这一次攻击者聪明了一点，把这一行的哈希也算对了。**但它算不出下一行**——第 4 行里写着“我的前一条是 3c7e…”，而那个值已经不存在了。所以报的是第 4 行，不是第 3 行。

这句话是整个演示的核心：**哈希链保护的不是单条记录，是记录之间的关系。** 单条可以伪造，关系不能。

## 4. 攻击三：重写整条尾链（必须自己讲出来）

```
[8] 重写整条尾链：改 seq 3 并重算其后所有 hash（文档记载的盲区）
    -> 符合预期  链依然自洽，无异常上报
```

**台词**：这个我挡不住。**有写权限的人把后面每一行的哈希都重算一遍，链就是自洽的**；删掉最后几行也一样。这不是实现缺陷，是哈希链的固有性质——它证明「已记录的部分没被改」，不证明「没有整段被替换」。

要封住它需要外部锚定：把链头哈希签名，或者把末条哈希打进 git tag / 只追加日志。**这不在本项目范围内，我把它写进了 DESIGN 局限 7**，而不是假装没有。

## 5. 收尾：fail-closed（这一步最容易被跳过，但最值钱）

```powershell
.venv\Scripts\python.exe scripts\failclosed_demo.py
```

```
S2  拔掉写权限（真实 chmod，非模拟）：网关拒绝启动
  网关退出码 = 3（约定 3 = 拒绝启动）
  原链字节未变：True；verify：OK: 2 条记录，链完整

S3  [注入] 运行中写盘失败：结果丢弃、run 中止、后续调用被拒
  stats: records_written=1, results_delivered=1, calls_attempted=3
  记录行数=1  verify=OK: 1 条记录，链完整
```

**台词**：哈希链有一个盲区是「漏记」——删掉尾巴它一样通过。所以唯一的防线是**记录不下来就不执行**：写盘失败，这次调用的结果直接丢弃，run 中止，后续调用一律拒绝。上面这行 `results_delivered=1, records_written=1` 就是它的证据：**交付给模型的结果数，从来没有超过写下来的记录数。**

S2 那段不是打桩，是真的把文件设成只读。S3 那段是注入的，所以我标了 `[注入]`——**这个项目里，模拟的东西必须自己说清楚是模拟的。**

## 6. 录屏时的三个镜头

| 镜头 | 命令 | 时长 |
|---|---|---|
| 一 | `echo_client.py` 正常跑完 + verify PASS | 8 s |
| 二 | `tamper_demo.py` 里第 7、8 两例 | 12 s |
| 三 | `failclosed_demo.py` 的 S2 + S3 结论行 | 10 s |

镜头二和镜头三**必须在同一个录屏里连着放**：先证明能检出，再主动说出检不出的是什么。顺序反了就成了辩解。

## 7. 常见追问与答法

| 追问 | 答 |
|---|---|
| 那我把整条链重写不就行了？ | 能，所以需要外部锚定。这是我的局限 7，不是我没想过 |
| verify 通过能说明没少调用吗？ | 不能。它只说明已记录的部分没被改。少调用要靠 fail-closed 挡，两条一起才成立 |
| 为什么报第 4 行不是第 3 行？ | 因为第 3 行被重算过，自洽了；断的是它和第 4 行之间的关系 |
| 记录里为什么不存参数和结果？ | 存摘要就够了，且不会把客户数据复制进证据文件。要复核时用 `args_hash` 比对，不需要看原文 |
